# Architecture Decision Records

Format: decision, context, consequence. Append-only. A coding agent must not deviate from an accepted ADR; it must raise a new ADR instead.

---
### ADR-001 — Extend the existing backend skeleton
**Accepted.** `backend/` already holds a Node/TS/Express/Prisma skeleton (layered structure, `AppError`, `handleApiResponse`, zod validation, constants, husky/eslint/prettier, one baseline migration). We extend it rather than start over.
*Consequence:* skeleton conventions (`@constant`, `@middleware`, `@routes` path aliases, `END_POINTS`, `RES_STATUS`) are binding. Its `User`/`UserRole` baseline model is replaced in M0 by the real identity model via a new migration — the applied baseline migration is not edited.

---
### ADR-002 — Separate `Users` (members) and `AdminUsers` (staff)
**Accepted.** Two identity tables, two JWT audiences (`aud: member` / `aud: admin`), two auth middlewares.
*Context:* members and staff have different lifecycles, different credential policies and different attack surfaces; RBAC applies only to staff. Elvee does the same.
*Consequence:* no privilege escalation path from a member token; slight duplication in auth code, contained in a shared `AuthService` base.

---
### ADR-003 — DB naming: Elvee-identical
**Accepted.** Tables `PascalCasePlural` (`MembershipApplications`), columns `snake_case` (`submitted_at`), audit timestamps camelCase (`createdAt`, `updatedAt`, `deletedAt`). Achieved with Prisma `@@map` / `@map`.
*Consequence:* raw SQL must double-quote identifiers (`FROM "Members" m`). Documented once, applied everywhere. Team moves between Elvee and this project without relearning.

---
### ADR-004 — Payload + response encryption, Elvee scheme
**Accepted.** AES-256-CBC (`crypto-js`) over gzip (`pako`), env keys `CHIPER`/`TERIFF`/`PLAN`, request `{data: ciphertext}`, response `data` encrypted, `decrypted_data` echoed only when `APP_ENV=local`.
*Context:* user requirement — parity with Elvee so frontend utils, Sentinel and team habits carry over.
*Consequence:* static IV per environment is weaker than a per-message IV (R-5); accepted for parity. Encryption is obfuscation, **not** authorization — authn/authz/validation still run on every request. Exceptions: multipart uploads, gateway webhooks, health endpoint.

---
### ADR-005 — Hybrid read strategy
**Accepted.** Prisma typed client for point reads and simple relations; parameterised `$queryRaw` for list/search/report/dashboard queries (joins, aggregates, filters, sorts).
*Context:* skeleton `RULES.md` mandates raw SQL for all reads; that costs type safety and velocity on trivial reads.
*Consequence:* `RULES.md` is amended in M0 to match. Every raw query is parameterised (never string-concatenated), returns only needed columns, and paginates. Repository functions expose typed return DTOs regardless of the read mechanism.

---
### ADR-006 — No polymorphic foreign keys
**Accepted.** Master instructions ban them without explicit approval, and none is requested.
*Consequence:*
- Documents: separate `ApplicationDocuments` and `MemberDocuments` tables, both FK to `DocumentTypes`, instead of one `documents(owner_type, owner_id)` table.
- Approvals: `ApprovalRequests` carries explicit nullable FKs (`application_id`, `profile_change_request_id`) plus a `subject_type` enum and a CHECK constraint that exactly one FK is set.
- `AuditLogs` keeps `entity_name` + `entity_id` as a **non-FK soft reference** (an audit row must survive deletion of its subject) — the one documented exception, no join is ever performed on it.

---
### ADR-007 — Money and numbering
**Accepted.** All monetary columns `Decimal(14,2)` (Prisma `@db.Decimal(14,2)`), currency column `char(3)` default `INR`. Human-facing numbers (`invoice_number`, `receipt_number`, `member_code`, `payment_number`) generated by a transactional sequence helper with a DB unique constraint; format per A-12 pending OQ-8.
*Consequence:* no float arithmetic anywhere; totals recomputed server-side, never trusted from the client.

---
### ADR-008 — Payment provider abstraction with a Manual provider in MVP
**Accepted.** `PaymentProvider` interface (`createOrder`, `verifySignature`, `fetchPayment`, `refund`). MVP ships `ManualProvider` (admin records an offline/NEFT payment) and `MockProvider` (tests). The real gateway lands as one adapter file once OQ-4 is answered.
*Consequence:* M5 is not blocked by the provider decision; the invoice/payment state machine is provider-agnostic and webhook handling is idempotent from day one.

---
### ADR-009 — In-process cron for MVP
**Accepted.** `node-cron` in the API process, guarded by an `ENABLE_JOBS` env flag so only one instance runs jobs.
*Consequence:* simple deploy; if the API is horizontally scaled, only the flagged instance schedules. Revisit if multi-instance is needed.

---
### ADR-010 — Notifications are queued rows, not inline sends
**Accepted.** Services insert into `Notifications` inside the same transaction as the business change; a job drains and dispatches per channel with retry + backoff.
*Consequence:* a failing SMTP/WhatsApp provider can never roll back or block an approval; delivery is observable and replayable.

---
### ADR-011 — Approval workflow is data-driven, config UI is read-only in MVP
**Proposed** (needs OQ-3). Stages/approver-roles live in `ApprovalWorkflows`/`ApprovalStages` and are seeded; the admin UI lists them read-only for MVP; full stage editing UI is a post-MVP toggle.
*Consequence:* engine is configurable from day one without spending MVP time on a workflow builder UI.

---
### ADR-012 — Admin app is React + Vite (not Next.js)
**Accepted.** `CLAUDE.md` specifies React for admin; no SEO/SSR need.
*Consequence:* differs from Elvee admin (Next.js). All Elvee admin patterns that are framework-agnostic (Redux slices, axios service layer, enc-dec, AntD theming, permission hooks) still port; Next-specific ones (`app/` routing, server components) are replaced by React Router v6.

---
### ADR-013 — Every table and every column carries a database comment
**Accepted** (user requirement, 2026-08-12). No table and no column may exist in PostgreSQL without a `COMMENT ON`.

*Context:* Prisma does **not** propagate `///` schema doc-comments to the database. `\d+` and every DB tool would otherwise show a bare schema, and the meaning of a column would live only in TypeScript. Elvee already sets `comment:` on Sequelize columns; this is the Prisma equivalent, made mandatory and machine-checked.

*Mechanism:*
1. Every Prisma model/field gets a `///` doc-comment (source of truth, visible in the client types).
2. After `prisma migrate dev` generates `migration.sql`, the migration owner appends a `COMMENT ON TABLE` / `COMMENT ON COLUMN` block covering every table and column the migration created or altered, in the same file, inside the same migration.
3. `npm run db:check-comments` fails the build if any table or column in the `public` schema (excluding `_prisma_migrations`) has a NULL comment. Runs in husky pre-push and in every module's self-test.

*Consequence:* migrations are longer; the schema is self-documenting in psql, pgAdmin, DBeaver and any generated ERD. A migration that adds a column without a comment does not pass the gate.

### ADR-014 — Framework and runtime versions pinned
**Accepted.** Node 24 LTS, PostgreSQL 18, Express 4.21, Prisma 6, TypeScript 5.7, Next 14 + React 18, Vite 6 + React 18, AntD 5, Tailwind 3.4, zod 3. Full table in `versions.md`.
*Context:* two agents building in parallel will otherwise pick different majors (Express 5 vs 4, Next 15/React 19 vs 14/18, Tailwind 4 vs 3) and the shared `ui/` components stop porting between the apps.
*Consequence:* no major bumps during MVP. Express 5 and Next 15/React 19 are deliberately deferred — no MVP benefit, real regression risk against the AntD 5 + Elvee-parity stack.

---
### ADR-015 — Notification outbox belongs to the foundation, not to M8
**Accepted.** `NotificationTemplates`, `Notifications`, the drain job and `EmailChannel` are built in M0/M1, not in the communication cycle.
*Context:* review found a dependency inversion — signup OTP and password-reset emails (M1) and approval emails (M4) all need delivery long before the communication module. The original plan would have forced direct SMTP calls early and a rewrite later.
*Consequence:* M8 shrinks to notices/circulars, audience targeting, the WhatsApp channel and the admin outbox UI. Every earlier module queues rows against a mechanism that already exists.

---
### ADR-016 — Member record is created at application start, not at approval
**Accepted.** A `Members` row (status `DRAFT`) is created when a signed-up user starts an application. `MembershipApplications` references it and stores the submitted values as an immutable snapshot.
*Context:* the original plan created `Members` only inside the final-approval transaction, which made the profile/KYC module unbuildable before the approval module and forced a field-by-field copy step.
*Consequence:* profile, contacts, addresses and KYC documents attach to a stable `member_id` from day one. Approval flips `DRAFT → PENDING → ACTIVE`, assigns `member_code`, and creates the term + invoice. The application snapshot is what the approver saw and is never mutated after submission. `Members.status` gains `DRAFT`. Supersedes assumption A-8's "copy on approval" wording.

---
### ADR-017 — Storage behind an adapter, local driver for MVP
**Accepted.** `StorageAdapter` interface with `local` and `s3` drivers, selected by `STORAGE_DRIVER`. MVP runs `local` with `STORAGE_PATH` outside every web root. Rules in `file-storage.md`.
*Consequence:* OQ-10 (hosting/storage) stops blocking M0 and M3; switching to S3 is one file plus env.

---
### ADR-018 — Raw request body is captured in M0 for webhook signatures
**Accepted.** `express.json({verify})` stores `req.rawBody` from the foundation cycle onward.
*Context:* gateway webhook signatures are computed over exact bytes; `express.json()` discards them. Adding this in M5 would mean editing the frozen shared core.
*Consequence:* one line in M0; `payment-webhook-security.md` §3 works unchanged when the real gateway arrives.

---
### ADR-019 — Cycle order corrected (masters → members → application/approval → payments)
**Accepted.** Sequence is now: M0 foundation · M1 auth/RBAC · M2 masters & fees · M3 members, KYC, member management · M4 application, approval, activation, invoice issuance · M5 payments/refunds/reconciliation · M6 renewal · M7 events · M8 communication · M9 directory/public · M10 dashboard/reports/org/audit/settings.
*Context:* review found the original order unbuildable — the approval cycle (old M3) had to resolve a fee (old M4), create a membership term (old M6) and issue an invoice (old M5), all of which came later; and the application form's category/fee step needed masters that did not yet exist.
*Consequence:* every cycle's dependencies now point strictly backwards. Membership-term and invoice **schema + issuance** move into the approval cycle; the payments cycle keeps the gateway, receipts, refunds, reconciliation and dunning. Module ids M0–M10 refer to the order in this ADR.

---
### ADR-020 — `prisma.config.ts` pins the migrations directory
**Accepted (M0).** With a schema *folder*, Prisma 6.19 defaults migrations to `prisma/schema/migrations/`, which orphans the existing baseline and silently starts a second migration history. `prisma.config.ts` pins `migrations.path` to `prisma/migrations/` (and removes the deprecated `package.json#prisma` block).
*Consequence:* one continuous history; `migrate status` stays meaningful. Any agent adding a schema file must not move this path.

---
### ADR-021 — Partial unique indexes are hand-written SQL
**Accepted (M0).** Prisma cannot express `UNIQUE … WHERE "deletedAt" IS NULL`, which `database-design.md` §H requires on every soft-deleted table. They are written directly in the migration SQL.
*Consequence:* a drift check was run empirically — a following `migrate dev --create-only` produced an **empty** migration, so Prisma leaves them alone. Re-verify this after any Prisma minor upgrade; if a future version starts reporting drift, the indexes move to an `Unsupported`/`@@index` workaround or the check moves into the Sentinel `schema` suite.

---
### ADR-022 — Local-only self-test echo endpoint
**Accepted (M0).** `POST /api/v1/_selftest/echo` is mounted **only** when `APP_ENV=local`. It decrypts, zod-validates, and returns an encrypted body, so the whole encryption boundary is provable end to end before M1 lands a real POST route.
*Context:* the alternative was asserting that a 404 got past the decryption middleware, which proves almost nothing.
*Consequence:* verified 404 under `APP_ENV=dev`. It is an unauthenticated reflector and must never exist in a shared environment — same reasoning as `observability.md` §8's ban on a "decrypt this for me" endpoint. The Sentinel `crypto` suite targets it in local and retargets to a real business POST from M1 so the suite also works against dev/staging.

---
### ADR-023 — Env precedence: real environment beats files
**Accepted (M0).** Loader order is `process.env` > `.env.<APP_ENV>` > `.env`, and empty values in a file are ignored.
*Context:* the skeleton used `dotenv({override:true})`, so a blank line in `.env.production` would silently shadow an injected `DATABASE_URL`. The failure would present as a missing secret rather than a shadowed one — an expensive hour at 2am.
*Consequence:* injected/CI/orchestrator variables always win; fail-fast on genuinely missing keys still fires.

---
### ADR-024 — Database comments are generated from the schema, not hand-copied
**Accepted (M0).** `scripts/emit-db-comments.ts` reads the Prisma `///` doc-comments and emits the `COMMENT ON` block appended to each migration.
*Consequence:* ADR-013's "the `///` and the SQL must say the same thing" is mechanically true instead of a promise a reviewer has to police.
